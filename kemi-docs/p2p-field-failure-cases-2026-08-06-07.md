# KEMI P2P 现场失败案例、运营商差异与代码取舍（2026-08-06～2026-08-07）

## 1. 文档目的

本文单独记录两天内 MAC + 双屏 PAD 的真实 P2P 调试过程，回答四个问题：

1. 哪些网络可以直连，哪些网络只能中继；
2. 为什么现场电信热点可以直连，而联通热点连续失败；
3. MAC 已监听固定 `TCP 21118`，为什么公网仍然连不进来；
4. 两天加入的代码哪些应保留、哪些必须回退，以及后续应如何优化。

本文以真实日志为准，不把 STUN 成功、UDP Hole Punched、端口监听或 UPnP 调用成功单独当作 P2P 成功。只有最终会话类型为 `TCP`、`UDP`、`TCP-Mapped` 或 `IPv6` 才是直连；`Relay` 明确表示媒体经过 `hbbr:21117`。

相关机制说明：

- [p2p-network-debug-and-optimization.md](p2p-network-debug-and-optimization.md)
- [ipv4-p2p-fixed-port-mapping.md](ipv4-p2p-fixed-port-mapping.md)

## 2. 结论先行

- 电信热点的两次成功连接使用的是普通随机端口 `TCP with UDP punch`，不是固定 `21118`。
- 联通热点现场属于端点相关、变化明显的运营商 NAT。STUN 能得到一个公网映射，但对 MAC 目标发起连接时该映射不能稳定复用，普通随机端口和固定 `21118` 均快速失败。
- “电信可以、联通不行”是本次两个具体热点出口的 NAT 行为差异，不代表所有电信网络必然成功或所有联通网络必然失败。热点重拨、基站、APN 和运营商 NAT 池变化后结果可能改变。
- MAC 的 `21118` 确实在本机监听，但 MAC 位于两级 NAT 后。自动 UPnP 只完成内层映射，外层 TP-Link 没有转发，因此公网 `113.110.200.176:21118` 不可达。
- `1.4.73+180` 和 `1.4.74+181` 的重试/双路径实验没有改变网络可达性，却增加连接等待并改变候选竞速，应回退。
- 当前源码已恢复到 `3c177be17` 中的快速并行策略，并完成 `1.4.75+182` 候选包构建；只额外保留固定候选诊断过滤词。设备上现装的 `1.4.74+181` 仍是实验包，不能作为正式发布版本。

## 3. 连接阶段与容易误判的日志

```text
PAD
  ├─ 连接 hbbs:21116：交换设备、NAT与候选信息
  ├─ UDP NAT / STUN：查询当前打洞socket的公网映射
  ├─ Hole Punched：得到可尝试的对端候选，不代表已建立会话
  ├─ 并行尝试普通TCP、UDP/KCP、IPv6、TCP-Mapped:21118
  ├─ secure_connection：完成RustDesk身份与密钥握手
  └─ 最终类型 TCP/UDP/TCP-Mapped/IPv6 或 Relay
```

以下日志只能说明某一阶段完成，不能单独证明 P2P：

| 日志 | 准确含义 | 不能推导的结论 |
|---|---|---|
| `rendezvous server ...:21116` | 信令服务器可达 | 媒体一定直连 |
| `UDP punch socket mapped by STUN` | 该 UDP socket 得到公网映射 | 映射对其他目标仍保持一致 |
| `UDP/TCP Hole Punched` | 双方交换并生成了候选 | 候选已经通过TCP和安全握手 |
| `TCP *:21118 LISTEN` | MAC本机进程监听端口 | 公网路由器已把端口转入MAC |
| `UPnP returned 172.21.16.142:21118` | 内层路由建立了映射 | 最外层公网入口已建立映射 |
| `Failed to accept connection from ... deadline` | 某条接收/握手路径超时 | 固定21118已经从公网到达MAC |
| `Relay connection` | 连接成功但使用hbbr中继 | P2P成功 |

尤其是 `Failed to accept connection from <PAD公网IP>` 中的地址也被用于会话元数据，不能仅凭这一行认定公网 TCP 已穿透到固定 `21118`。必须结合最终连接类型、实际目标端口和外部端口探测判断。

## 5. 各场景逐项解释

### 5.1 同一局域网：正常直连

PAD 与 MAC 同在 `192.168.3.0/24` 时，对端候选是 `192.168.3.65:56063`。TCP 仅用 5.47ms 建立，最终类型为 `TCP`。

同网显示 TCP 而不是 UDP 不属于故障。只要没有 `21117` 媒体连接且最终类型为 TCP，就是局域网 P2P。

### 5.2 电信热点：普通随机端口成功

两次成功的共同特征：

- PAD热点公网地址保持为 `113.84.83.202`；
- STUN端口分别为 `65465`、`65440`；
- MAC信令候选分别为随机端口 `57139`、`57786`；
- 最终均为 `TCP connection with UDP punch`；
- TCP建立仅用 26.27ms 和 53.35ms。

这说明该电信热点在当时的运营商 NAT 池中，打洞时生成的状态足够稳定，PAD 可以访问 MAC 的随机候选并完成 RustDesk 安全握手。

它没有使用 `TCP-Mapped`，也没有依赖固定 `21118`。所以固定映射失败并不妨碍这两次普通打洞成功。

### 5.3 联通热点：STUN成功但映射不可复用

联通热点的公网地址为 `112.97.83.104`，连续会话的外部端口出现 `42600 → 8374 → 42612 → 9380 → 44102` 等明显变化。日志将 NAT 标为 `ASYMMETRIC`。

STUN只回答“访问这个STUN服务器时，运营商给当前socket分配了什么地址”。端点相关NAT可能在访问 hbbs、STUN、MAC公网IP等不同目标时重新分配端口。于是 STUN 地址虽然真实，却不一定能被 MAC 按同一端口反向命中。

实验包对 MAC 随机端口和固定 `21118` 的连接均在 21～70ms 内失败。这不是等待不够：远端路径明确快速拒绝/不可达。继续重复相同目标只会延迟中继。

### 5.4 为什么不是“联通完全不支持P2P”

运营商品牌不是协议能力开关。决定结果的是当次会话所在的：

- APN与运营商NAT池；
- NAT是否按目标地址/端口重新映射；
- 映射保持时间；
- 防火墙是否允许TCP/UDP出站和返回流量；
- 是否存在双方都可用的IPv6。

重拨热点或更换基站后，联通也可能进入不同NAT池；电信也可能遇到严格CGNAT而失败。因此客户端只能依据实时候选与最终握手判断，不能按运营商名称硬编码策略。

### 5.5 PAD处于级联Wi-Fi

现场提出过三类组合：

1. PAD与MAC都接入多个路由器级联的网络；
2. PAD在级联网络，MAC在另一普通网络；
3. PAD在手机热点，MAC在当前公司网络。

同一LAN只有在两端实际处于同一可互通子网时才成立。“都能访问互联网”和“都能访问信令服务器”不能替代局域网互通。级联路由若开启路由/NAT模式，会隔离下级设备并产生端点相关映射；正确网络优化是 AP/桥接/Mesh 模式，而不是在每一级继续增加客户端重试。

### 5.6 IPv6看似存在但不能使用

联通热点曾通过STUN发现 PAD 公网IPv6 `2408:...`，电信也曾发现 `240e:...`。但：

- PAD初始化IPv6 socket时仍出现STUN解析/绑定失败；
- MAC当前 `en1` 没有公网IPv6，仅有链路本地地址和隧道接口；
- P2P IPv6要求两端都具有可路由地址并允许防火墙入站。

因此本轮不能使用IPv6。发现单端公网IPv6不等于端到端IPv6可用。

### 5.7 `21114 API`错误不是本次原因

日志中的 `119.96.24.110:21114 Connection refused` 来自账户、审计、心跳API。当前开源服务器没有启用账户API，这是已知能力边界。

P2P信令 `21116`、中继 `21117`均正常，所以 `21114`不导致本次候选失败。它会制造日志噪声，后续可以降频，但不能把它当成P2P根因。

## 6. MAC固定21118为什么没有生效

现场只读检查确认：

```text
MAC                  192.168.3.65
默认网关             192.168.3.1
下级路由WAN          172.21.16.142
上级TP-Link网关      172.21.16.1
公网出口             113.110.200.176
MAC监听              TCP *:21118 LISTEN
```

`traceroute`路径为：

```text
192.168.3.65
  → 192.168.3.1
  → 172.21.16.1
  → 113.110.200.1
  → Internet
```

MAC映射线程每五分钟都报告：

```text
UPnP returned non-public address 172.21.16.142:21118
```

这表示只完成了：

```text
172.21.16.142:21118 → 192.168.3.65:21118
```

仍缺少：

```text
113.110.200.176:21118 → 172.21.16.142:21118
```

上级 `172.21.16.1` 的实测结果：

- UDP `5351`（PCP/NAT-PMP）：`Connection refused`；
- UDP `1900`（UPnP/SSDP）：`Connection refused`；
- TCP `80/443`：可访问，页面识别为 TP-Link 管理后台。

因此客户端无权自动建立第二层映射。监听端口相当于“MAC办公室分机已开”，但公网入口的“总机”没有把来电转给它。

### 6.1 当前网络的根本处理

最小变更是在上级 `https://172.21.16.1` 配置虚拟服务器：

```text
协议：TCP
外部端口：21118
内部IP：172.21.16.142
内部端口：21118
状态：启用
```

同时为下级路由固定 `172.21.16.142`。下级路由已经由KEMI请求 UPnP 映射；正式部署更稳妥的做法是下级也设置静态 `21118 → 192.168.3.65:21118`，并固定MAC地址。

如果级联路由只是用于增强Wi-Fi，最佳结构是把下级路由改为 AP/桥接模式，消除一层NAT，再由上级直接把 `21118` 转给MAC。

## 8. 为什么当前实验代码会让电信也感觉变慢

原稳定策略中，电信热点在普通随机端口TCP完成后立即返回，固定21118失败不会阻塞赢家。

实验代码加入了以下额外行为：

- 对普通端口和固定21118重复连接；
- 在UDP映射后主动再发起一轮TCP PunchHole；
- 第一轮失败后不允许马上中继，等待第二轮接管；
- 多个复用同一本地打洞地址的socket竞争，增加调度和NAT状态数量。

理论上第一轮若在26～53ms内成功仍应较快返回，但实际移动网络的打洞时间会波动；一旦超过实验设置的启动点，第二轮请求和多组重试会同时出现，用户就会感到明显变慢。该复杂度没有换来联通直连，因此不应保留。

## 9. 后续优化优先级

### P0：先恢复稳定速度

1. 使用 `1.4.75+182` 构建PAD；
2. 覆盖安装到副屏；
3. 同LAN、电信热点、联通热点分别测试至少3次；
4. 电信热点成功时应恢复约1秒打洞加几十毫秒TCP握手；
5. 联通不可直连时应快速进入中继，不能再固定增加2秒。

### P0：打通MAC公网固定入口

1. 在最外层 TP-Link 配置 `21118 → 172.21.16.142:21118`；
2. 固定两级路由的目标IP；
3. 使用真正的外部网络探测 `113.110.200.176:21118`；
4. MAC日志必须从 `non-public address` 变为可验证的公网固定入口；
5. PAD联通热点应优先出现 `TCP-Mapped`，否则再查PAD是否限制出站21118。

### P1：让应用准确展示“监听”和“公网可达”是两件事

建议MAC状态拆为：

- 本机监听：`21118 LISTEN`；
- 内层映射：网关返回的地址；
- 公网验证：由可信云探针从外网连接一次21118；
- 最终状态：`公网直连入口可用/多级NAT未打通/映射协议关闭`。

可由自建 hbbc/hbbs 增加轻量端口探测接口。它只验证TCP握手，不转发屏幕数据，不等同中继。没有外部探针时，不应仅凭UPnP调用结果显示绿色“公网可用”。

### P1：只在确认映射可用时下发固定候选

当前PAD会并行尝试信令公网IP的固定21118。后续可扩展带认证、有效期的候选字段：MAC在映射并经外部探针验证后上报 `external_ip:port`，hbbs只向当前认证会话下发。这样未映射网络不再做无意义的21118尝试，也能支持网关分配的非固定端口。

### P2：IPv6与高级NAT穿透

- 双端均有公网IPv6时优先IPv6；
- 收集不同APN下的映射一致性，而不是按运营商名称写死；
- 对称NAT可以研究更完整的ICE候选和端口预测，但不能承诺成功；
- 如果两端都没有可控公网入口，唯一可保证连接的仍是中继。

## 10. 标准验收记录格式

每次网络测试至少记录：
