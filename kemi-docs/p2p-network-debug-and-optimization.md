# KEMI IPv4 P2P 调试、失败处置与优化决策（2026-08-06）

## 结论先行

MAC获得一个可从公网访问的**固定公网IPv4:21118映射**，会显著提高“PAD在级联Wi-Fi或手机热点、没有IPv6”时的直连机会，但**不能保证任何PAD网络都P2P成功**。它提供的是一条由PAD主动向MAC公网端口发起的`TCP-Mapped`候选路径；MAC侧映射必须真实位于最外层公网出口、端口可达，PAD侧也必须允许对该公网TCP端口出站连接。任一条件不满足，正确且安全的结果仍是`Relay`中继，而不是假报P2P成功。

本文档范围为KEMI PAD控制KEMI macOS。它记录2026-08-06现场的真实证据、当前候选实现和后续验收方法；不是“保证打洞成功”的承诺。

## 1. 连接类型与数据流

会话始终先经`hbbs`交换身份、在线状态和候选信息；这不等于画面一定走服务器。建立成功后，画面、输入和文件传输可能走以下任一承载路径：

| 连接类型 | 实际路径 | 是否占用`hbbr`媒体带宽 | 适用条件 |
|---|---|---:|---|
| `UDP` | 两端公网UDP候选完成打洞 | 否 | 两侧NAT/防火墙允许对应UDP流量 |
| `TCP` | 两端已有的可达TCP直连候选 | 否 | 同一LAN或普通IPv4直连可达 |
| `TCP-Mapped` | PAD主动连接MAC公网`IPv4:21118` | 否 | MAC真实固定映射 + PAD允许出站TCP |
| `IPv6` | 两端可路由IPv6直接连接 | 否 | 双方IPv6真实可用且防火墙允许 |
| `Relay` | 双方分别连`hbbr`，服务器转发媒体 | 是 | 上述候选均失败或超时 |

连接竞争必须并行：普通UDP/TCP候选与`TCP-Mapped`同时尝试，任一先完成RustDesk原有加密、身份认证和会话握手即胜出。不能为了等待映射而串行阻塞现有路径，更不能因新路径失败影响原本可用的中继回退。

```text
PAD发起控制MAC
  │
  ├─ hbbs交换MAC公网候选、NAT类型、会话认证信息
  ├─ 并行：普通UDP / 普通TCP /（MAC可映射时）公网IP:21118 TCP-Mapped
  ├─ 第一个完成认证的候选承载会话
  └─ 全部失败 → hbbr Relay（仍可控制，不把失败留给用户）

MAC侧（必须由真实主服务生命周期管理）
  │
  ├─ RustDesk直连监听TCP 21118
  ├─ PCP → NAT-PMP → UPnP IGD请求“外21118 → 内21118”
  ├─ 校验外部IP必须是公网IPv4、外部端口必须仍为21118
  └─ 成功后租期续租；失败记录原因，不阻塞正常会话
```

## 2. 今天现场网络证据

通过MAC“调试日志”按钮导出的PAD日志，PAD当时为`192.168.43.11`，没有可用IPv6；STUN得到映射`112.97.82.108:3593`，MAC对端候选为`113.110.200.176:52350`。双方NAT判定为`ASYMMETRIC`，最终会话使用中继。

这解释了以下三类现象：

1. PAD接入多Wi-Fi级联网络时失败：至少有一层NAT会为不同目的地重写UDP端口，远端看到的映射不可预测，普通UDP打洞难以同时命中。
2. PAD在该级联Wi-Fi、MAC在另一网络时失败：两端都不是同一二层LAN，且PAD无IPv6，必须靠公网IPv4候选；对称NAT使标准UDP候选不能稳定复用。
3. PAD接入手机热点、MAC在当前网络时失败：热点通常在运营商CGNAT之后，PAD无法要求运营商把入站端口转给自己；普通UDP打洞也常被对称/受限NAT破坏。

“ADB可连、两端能访问外网、能连信令服务器”只说明已有某条TCP/中继通路可用；它不能证明PAD与MAC之间存在可达的公网P2P通路。反过来，同一局域网显示`TCP`而不是`UDP`也不是故障：候选竞争中TCP先完成握手即可胜出，仍是不经`hbbr`的直连。

## 3. MAC固定公网映射：能解决什么，不能解决什么

### 3.1 它如何帮助PAD

PAD无需拥有公网IP，也无需接收入站连接。只要它能正常**向外发起**TCP连接，便可主动连接MAC的公网`IPv4:21118`。因此它特别有机会改善：

- PAD在运营商手机热点、无IPv6且入站完全不可达；
- PAD在多级Wi-Fi后、其自身UDP打洞为`ASYMMETRIC`；
- PAD和MAC位于不同网络，普通UDP候选被对称NAT阻断。

这条路径是“PAD出站 → MAC入站”，不是让MAC反向穿透PAD热点。因此对PAD所在网络的要求被降低为：DNS/公网路由可用、允许向MAC公网IP的TCP 21118发起连接、没有企业代理/白名单拦截该端口。

### 3.2 为什么不能说“无论PAD是什么网络都一定成功”

以下任一情况都可能失败，仍需中继：

| 失败点 | 为什么固定映射也无效 | 可否补救 |
|---|---|---|
| MAC映射只创建在内层路由器 | 外层路由仍不知道21118应该转给谁 | 可：外层做端口转发，或外层桥接/DMZ到内层，再由内层转MAC |
| MAC出口是CGNAT（`100.64.0.0/10`等） | 运营商公网地址不归MAC路由器控制 | 通常不可由客户端补救；申请公网IPv4/IPv6，或继续中继 |
| 路由器拒绝PCP/NAT-PMP/UPnP或只能随机外部端口 | PAD只知道固定候选21118，不能猜随机端口 | 可：管理员手工固定21118；未来扩展受认证的候选端口上报协议 |
| MAC防火墙/本机监听未放行 | 包到达MAC公网出口但无法完成会话 | 可：修复监听、macOS防火墙和端口转发链 |
| PAD网络封锁出站21118、强制代理/门户未认证 | PAD不能主动访问MAC公网端口 | 可能不可控；换网络/允许策略，或中继 |
| 企业深度检测、运营商流量策略、瞬时丢包 | TCP握手或RustDesk认证被阻断/超时 | 部分可通过重试、保活和备用端口策略改善，不能承诺 |
| 两端IP/候选过期或网切换 | 信令中的旧候选已失效 | 可：重新注册候选、重新连接；不应沿用旧会话状态 |

所以针对“多Wi-Fi级联的PAD，MAC获得公网IPv4固定映射后是否无论PAD怎样都能P2P”的准确回答是：**不是无条件成功，但这是目前最有效、对PAD侧侵入最小的IPv4补救路径。** 它把原本“两端都要成功UDP打洞”的问题变为“PAD只要可出站TCP，MAC必须真实可入站”。

### 3.3 多级路由的硬规则

MAC位于多级路由时，映射必须落在持有公网WAN地址的**最外层出口**。例如：

```text
Internet 公网IPv4
    │
外层路由 WAN（必须转发TCP 21118）
    │
内层Wi-Fi路由（必须转发/DMZ TCP 21118）
    │
MAC:21118
```

仅在内层路由看到“UPnP成功”不代表外网可达。自动映射只能访问MAC默认网关；若默认网关不是最外层，仍需网络管理员在上级逐层转发、设DMZ/桥接，或把MAC接到最外层路由。公网IP检测、外部端口等于21118、外部网络实测TCP连通三者必须同时成立。

## 4. 当前候选实现与已知边界

当前源代码的候选改动为：

- `src/kemi_p2p_portmap.rs`：MAC按`PCP → NAT-PMP → UPnP IGD`申请并续租固定TCP 21118；拒绝私网、回环、CGNAT外部地址及随机外部端口。
- `src/rendezvous_mediator.rs`：真实直连监听就绪后触发映射生命周期。
- `src/client.rs`：目标MAC为`ASYMMETRIC`时，将`MAC信令公网IP:21118`作为并行`TCP-Mapped`候选。
- `src/common.rs`与`src/client.rs`的UDP探测：保持同socket STUN回退、有限等待NAT结果和延后TCP-only回退，避免过早把UDP端口报成0；所有等待均应有上限，不能拖慢原连接。

两项不能省略的安全/正确性规则：

1. 固定映射只暴露已有RustDesk直连监听，连接仍经原有加密和设备身份认证；它不新增HTTP、Shell或未认证文件服务。
2. 不能把“路由器调用成功”当作直连成功。只有会话实际显示`TCP-Mapped`、`TCP`、`UDP`或`IPv6`才是P2P，`Relay`仍是中继。

### 4.1 今天的无效实验与正确修复方向

曾尝试从Flutter UI的`main_start_service`另起`start_server(true, false)`来启动映射。该做法会与已运行的MAC主服务竞争本地Unix IPC（如`/tmp/RustDesk-501/ipc`），使App无法正常打开；它已经被认定为错误架构，**不得重新使用**。

正确做法是把端口映射挂到已经拥有直连监听和IPC的真实后台服务生命周期：监听成功后启动，进程退出时停止，网络变更时重新校验。任何MAC测试构建仅可写入独立备份/测试位置；在用户设定的保护时段内不得替换正在运行的`/Applications/KEMI-远程桌面.app`。

另一个已发现问题是部分网络下默认网关信息可能无法由库读出；实现应记录该原因并继续尝试可用的UPnP发现路径，不能因为“未读到网关字段”就宣称所有协议失败。最终仍须以外部端口和外网实测为准。

## 5. 失败后的处理流程

```text
连接结果不是P2P
  │
  ├─ 日志是否出现TCP-Mapped候选？
  │    ├─ 否：检查MAC监听/映射生命周期、候选注册、版本是否一致
  │    └─ 是：继续
  │
  ├─ MAC是否报告“公网IPv4:21118 ready”？
  │    ├─ 否：检查UPnP/PCP/NAT-PMP、MAC是否在CGNAT、是否是多层内网
  │    └─ 是：继续
  │
  ├─ 外部网络能否TCP连接MAC公网IP:21118？
  │    ├─ 否：逐层端口转发、MAC防火墙或运营商/公司网络限制
  │    └─ 是：继续
  │
  ├─ PAD日志是否可向外连接且无门户/代理限制？
  │    ├─ 否：更换PAD网络、完成认证或让网络管理员放行
  │    └─ 是：候选/握手超时，保留日志并检查版本、信令候选和协议
  │
  └─ 任意阶段未满足：立即稳定回退Relay，不反复卡在“连接中”
```

建议由MAC连接页的“调试日志”一次性导出双方会话日志，按钮结果只显示“调试日志已获取”或“获取失败”。关键检索词为：

- `ASYMMETRIC`、`UDP`、`TCP`、`Relay`；
- `KEMI P2P mapped direct TCP port ready`；
- `automatic fixed-port mapping unavailable`；
- `KEMI trying mapped direct TCP candidate`；
- 最终会话类型`TCP-Mapped`或`Relay`。

## 6. 优化优先级与分工

### P0：不回归现有连接

- 普通UDP/TCP、局域网直连和`hbbr`中继始终并行可用；新候选不能串行等待、不能改变原端口语义。
- 只有真实MAC后台服务拥有端口映射生命周期；不得从Flutter页面重复启动服务或创建第二套IPC。
- 映射失败、路由切换和续租失败只记录并回退，不可使MAC App、现有会话或用户界面崩溃。

### P1：把固定映射做成可验证闭环

1. 在隔离Mac测试包中启动真实监听和映射，确认日志返回固定公网IPv4与外部端口21118。
2. 由第三方外网（不是同LAN）实测TCP 21118可达。
3. PAD分别接入级联Wi-Fi、手机热点和普通Wi-Fi，检查是否实际出现`TCP-Mapped`。
4. 同网、不同网、MAC重启、网络切换各复测一次；失败必须秒级回退Relay。

### P2：处理随机端口和更复杂网络

若路由器只能分配随机公网端口，不能让PAD猜测。需与自建`hbbs`一起扩展一个有认证、有效期和端口校验的候选上报协议：MAC成功映射后上报`external_ip:external_port`，hbbs只向已认证会话的PAD返回短时有效候选，PAD并行尝试。该项涉及客户端与服务端协议兼容、重放防护和过期清理，未实施前不能作为发布承诺。

IPv6是长期最干净的路径：PAD和MAC均有可路由IPv6时不需要IPv4端口映射。但今天PAD没有可用IPv6，不能把“系统开关显示IPv6”当成能力已具备。

## 7. 验收表：哪些情况有救

| 场景 | 标准UDP打洞 | MAC固定21118映射后的预期 | 最终处理 |
|---|---|---|---|
| 同一普通LAN | 通常可直连，可能显示TCP | 不必依赖映射 | 直接连接，TCP/UDP均可接受 |
| PAD级联Wi-Fi，MAC公网映射真实可达 | 常因`ASYMMETRIC`失败 | 有较高机会走PAD出站`TCP-Mapped` | 先测映射；不通则Relay |
| PAD手机热点，MAC公网映射真实可达 | 常失败 | 有较高机会走`TCP-Mapped` | 不要求PAD端口映射；不通则Relay |
| MAC多级路由但仅内层映射 | 常失败 | 仍失败 | 外层逐级转发/DMZ/桥接，或Relay |
| MAC处于CGNAT | 常失败 | 无法靠本地UPnP解决 | 公网IPv4/IPv6/网络管理员支持，或Relay |
| PAD企业网封锁出站21118 | 视策略而定 | 仍可能失败 | 放行、换网，或Relay |
| 两端有真实IPv6 | 无需依赖IPv4 | 应优先IPv6 | 记录IPv6直连并保留其他回退 |

## 8. 与已有文档的关系

`ipv4-p2p-fixed-port-mapping.md`是固定端口机制和发布验收的简版说明；本文档是今天现场调试、网络判断和失败处置的完整运行手册。发布前应同时阅读两份文档，并以实际会话类型和外网连通验证为准。

## 9. 2026-08-07 手机热点候选路径修正（MAC优先验证）

昨天手机热点场景的关键失效链是：PAD被信令判断为对称NAT后，MAC端在收到`PunchHole`
请求时直接生成中继；而非双屏PAD又被KEMI策略禁止发起中继，导致固定端口候选还没有尝试
就结束。

本次先修改MAC/Rust核心：

- `kemi_p2p_portmap`增加映射就绪状态。只有最近一次PCP、NAT-PMP或UPnP固定`TCP 21118`
  续租成功时才允许绕过“对称NAT立即中继”的提前分支；映射失败仍保持原有安全回退。
- MAC收到对称NAT打洞请求且固定映射就绪时，继续发送正常打洞响应，让PAD主动尝试
  `MAC公网IPv4:21118`，连接仍经过原RustDesk加密和身份认证。
- 直连候选在非局域网场景下不再只受`ASYMMETRIC`标签限制，普通TCP、UDP和固定端口候选
  并行竞争；固定端口不可达时快速失败，不阻塞原有成功路径。

这不是“所有手机热点必然P2P”的承诺。MAC必须真实拥有公网IPv4固定映射，PAD网络必须允许
出站TCP 21118；否则应明确记录失败并由双屏PAD按策略回退中继。验收日志重点看：

```text
KEMI P2P mapped direct TCP port ready
KEMI trying mapped direct TCP candidate
TCP-Mapped / Relay
```

本次先只验证MAC端构建和真实日志，再同步PAD及其他客户端，避免同时改变多端导致问题来源
无法区分。
